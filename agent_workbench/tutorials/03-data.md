# 03 · SQLite、事务与状态恢复

代码入口是 `storage.py`。数据库默认位于 `var/agent_workbench.db`，首次启动创建表并按配置初始化账号和演示资料。目录已加入 Git 忽略规则。

## 表之间的关系

`users` 是身份主体，`sessions` 存储登录会话。`documents` 保存当前资料，`document_versions` 保留历史版本。`conversations` 属于用户，`messages` 属于会话。每次请求产生一个 `runs`，运行步骤存入 `events`。`drafts` 是待确认内容，确认后产生 `tickets`。`audits` 记录重要业务动作。

不要把对话上下文、知识库、运行状态混为一种“记忆”。它们的更新频率、访问控制和保留规则不同。

## 事务为什么重要

创建工单需要一起完成：检查草稿状态、插入工单、更新草稿、写审计。如果中途失败，事务回滚，避免出现“工单已创建但草稿仍待确认”的状态。

`BEGIN IMMEDIATE` 在执行读改写前取得写事务，避免两个确认请求同时通过状态检查。`tickets.draft_id` 的唯一约束提供第二道保证。应用检查与数据库约束共同保护幂等性。

## 运行状态

```text
queued -> running -> completed
                 -> failed
```

每个会话通过部分唯一索引只允许一个活动运行。状态完成后，结果和助手消息保存到数据库。事件单独保存，让浏览器断线后可以重放。

## 重启恢复的实际含义

单进程后台任务不会跨进程重启继续执行。启动时，系统把残留的 queued/running 标为 failed，错误码为 `server_restarted`，取消未完成任务的草稿，并保存提示消息。用户可以重新发送问题。

已经完成的草稿和正式工单会保留。重启后仍可以确认已完成任务的待确认草稿。这里实现的是可识别的中断处理和业务状态保留，尚未实现从某次模型调用中间自动重放。

## WAL 与连接生命周期

WAL 允许读取与写入更好地协作，但 SQLite 仍然只有一个写入者。连接设置忙等待，并在每次方法结束后关闭。小型单机应用易于部署；多进程队列和多副本应迁移到服务端数据库与任务系统。

## 实验与排查

创建一份工单草稿，停止服务再启动，确认草稿仍在。再观察测试 `test_restart_interrupts_run_and_preserves_completed_draft` 如何模拟未完成运行。

备份不能只在数据库活跃时随意复制主文件：WAL 可能还包含最新数据。应停服后复制整个数据目录，或使用 SQLite backup API。迁移前保留备份，并检查 `schema_version`。

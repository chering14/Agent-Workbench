# 09 · 工单确认、幂等与审计

代码入口：`TicketArguments`、AgentService 的 prepare_ticket 分支、`Store.prepare_ticket()` 与 `Store.decide_draft()`。

## 明确的用户意图

界面“生成工单草稿”把本次 intent 设置为 ticket。应用检查该字段后才允许草拟工具。普通问答时，即使模型请求该工具也会被拒绝。这避免仅凭模型猜测就开始写业务数据。

工单草稿包含标题、问题描述、优先级与创建者。它是本地数据库中的待确认记录，不是外部服务台系统里的工单。

## 确认绑定具体内容

草稿 ID 对应一份固定内容与一个拥有者。当前项目不提供原地修改草稿的接口，确认作用于显示的这份内容；如果需要编辑草稿，必须同时设计版本或内容摘要，让旧确认不能作用到新内容。

模型只能准备草稿。确认入口是需要登录、CSRF token 和所有权检查的 HTTP API，并且对应运行必须已经完成。

## 幂等性

幂等表示同一操作重复执行，最终效果与执行一次一致。网络重试、双击和页面重连都可能让确认请求重复到达。

```text
读取草稿 -> 是否已有工单？ -> 有：返回原工单
                        -> 无：校验 pending + 运行已完成
                              -> 插入工单 + 改为 approved + 写审计
```

该流程位于写事务中，数据库对 draft_id 设唯一约束。并发测试用两个线程确认同一份草稿，验证只产生一张工单。

拒绝后草稿变成 rejected，不能再批准。运行失败或审核拒绝会取消草稿。已经正式创建的工单不能通过“拒绝草稿”撤回。

## 工单状态与审计

员工可以看自己的工单；管理员可以看本租户工单并调整 open、in_progress、resolved。重要动作写入 audits，包括资料保存、创建、拒绝与状态变化。

当前审计表便于追踪业务操作，不是防篡改日志系统。正式合规场景还需要独立日志存储、保留规则、访问管理及时间同步。

## 对接外部平台时

外部 HTTP 请求和本地数据库无法直接共享 SQLite 事务。应该采用外部幂等键、事务消息或 outbox，让“请求已成功但响应丢失”可以查询并恢复。仅给请求加重试，可能造成重复工单。

练习：在确认后刷新页面，再次确认同一草稿；观察工单 ID 保持一致，并检查数据库唯一约束对应的测试。

# 01 · 业务问题与系统全景

企业员工往往不知道制度在哪里、操作步骤是否过期，以及问题未解决时应该提交什么信息。服务台重复回答相同问题，工单又经常缺少背景。这就是本项目的业务入口。

## 输入、输出与完成条件

输入是用户身份、当前问题、历史会话和允许访问的资料。输出可以是有依据的回答、请求补充信息、证据不足说明，或等待确认的工单草稿。正式工单是经过明确确认后的数据库记录。

一次任务成功，应该满足业务条件：回答确实解决了所问问题，或者正确地澄清、拒答和升级。HTTP 返回 200、模型返回文字、存在引用，都只能证明其中一部分。

## 系统的六层

| 层 | 代码 | 职责 |
| --- | --- | --- |
| 界面 | web/index.html、style.css、app.js | 输入、消息、来源、确认与学习中心 |
| API | server.py、schemas.py | 身份验证、输入验证、资源访问与事件输出 |
| 编排 | agent.py | 决策循环、工具路由、预算、引用校验、审核 |
| 模型 | providers.py | 规则演示或真实 HTTP 协议 |
| 检索 | retrieval.py | 权限过滤后的分段、匹配与排序 |
| 存储 | storage.py、auth.py | 用户、会话、资料版本、运行、工单及审计 |

依赖方向是入口调用业务，业务调用基础能力。数据库不依赖网页，模型适配器不决定用户权限。这样的边界让后续替换界面、模型或存储更容易。

## 一次提问如何流动

```text
浏览器 -> POST runs -> queued -> 后台 AgentService
                           -> 模型请求 search_knowledge
                           -> 应用按身份检索
                           -> 模型请求 finish_answer
                           -> 应用校验引用
                           -> 独立 reviewer 审核
                           -> 保存结果和消息
浏览器 <- SSE 阶段事件 <- completed / failed
```

## 技术选择的代价

FastAPI 提供 API 和参数验证；SQLite 让单机部署简单，事务保护确认流程；原生 HTML/CSS/JS 减少前端构建依赖；直接实现小型工具循环，方便学习每一条消息。

这些选择适合单进程、规模有限的学习与作品展示部署。高并发、多副本、企业 SSO、专业工单平台和大规模检索需要对应替换。作品的可信度来自清晰边界和验证证据，而不是给组件贴上“生产级”标签。

## 实验

关闭独立审核，再提同样的问题。规则演示会少一个决策步骤。真实模型是否因此降低质量，需要同一数据集比较。记录质量、延迟和费用三项，才能讨论额外角色是否值得。

理解检查：哪些决定应该由模型做？哪些权限和写操作必须由应用控制？

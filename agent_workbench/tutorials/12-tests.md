# 12 · 测试、评测与实验设计

代码入口：`tests/test_baseline.py`、`tests/test_application.py`、`evaluation.py`、`acceptance.py`。完整检查由 `scripts/test.ps1` 或 CI 执行。

## 四种验证

单元测试检查局部规则，例如分段重叠和参数校验。集成测试检查数据库、API、认证和工具协作。浏览器验证检查真实页面操作。模型评测检查代表性任务在真实模型上的质量、延迟和成本。

HTTP MockTransport 测试能证明协议组装和错误处理，不能证明真实网络可达或供应商模型表现。

## 重点测试读法

工单测试先断言没有正式工单，再确认两次，断言只有一张。伪造引用测试让假模型连续返回假 chunk_id，确认内容没有被发布。越权测试改变实际登录身份，检查资料、运行和草稿无法被跨用户读取。

这类测试关注业务约束，比单纯断言“某个函数被调用一次”更能保护行为。

## 两套自带评测

`eval` 保留 M0 的 10 条合成检索回归用例。`app-eval` 在临时数据库上执行完整应用的代表性流程，生成版本化 JSON 报告。它们适合发现工程回归，不代表真实企业任务成功率。

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m agent_workbench eval
.\.venv\Scripts\python.exe -m agent_workbench app-eval
```

## 建立真实评测集

每条样本至少记录问题、允许身份、预期状态、相关资料、关键事实和不可接受的结果。覆盖正常问题、资料缺失、相关但无答案、多轮澄清、越权、恶意资料、工单和接口失败。

把数据分为开发集与留出集。开发集用于改提示和算法；留出集用于判断是否真的改进。人工标注要有一致规则，模型打分需与人工样本校准。

## 对比实验

比较单 Agent 和带审核方案时，固定模型、数据、提示版本、预算和运行条件。记录任务成功率、引用支持率、错误拒答、调用次数、p50/p95 延迟及费用。小样本不要把很小的差异解释成稳定收益。

改动失败时保留失败案例与原因，不放宽期望来掩盖问题。报告应写数据版本、样本数、模式、模型、运行时间和限制。

## Windows 测试等待

某些受限沙箱会阻止 asyncio 的本地 socketpair，表现为 TestClient 卡在事件循环创建。使用 faulthandler 查看线程栈可区分环境限制与业务死锁。应在允许本地套接字的环境重试，不能通过跳过 API 测试获得虚假的通过。

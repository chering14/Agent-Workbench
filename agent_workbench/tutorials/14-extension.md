# 14 · 功能修改与技术答辩

项目完成后的调整应沿现有边界进行：先定义输入输出与验收行为，再修改实现，最后验证回归和业务效果。

## 例一：增加工单类别

1. 在 TicketArguments 添加受限类别字段，并更新模型工具说明。
2. 数据库新增字段并编写 schema 迁移；保留旧数据默认值。
3. 草稿、确认和正式工单都传递类别，界面展示并允许适当选择。
4. 更新规则演示、模型协议样本和工单流程测试。

只改网页会让模型、存储和 API 的数据不一致。数据契约变更应沿整条链检查。

## 例二：对接专业工单平台

保留草稿与确认 API，在确认服务中增加外部适配器。使用草稿 ID 作为外部幂等键，保存外部 ID 与同步状态。处理成功响应丢失、超时、查询恢复和重试上限。

外部写入必须根据用户明确确认执行，不能让模型决定绕过。需要测试“外部已创建、本地尚未记录”的恢复行为。

## 例三：引入向量与混合检索

新增 embedding 接口、资料版本索引和向量存储实现，在 Retriever 层融合结果。权限过滤必须覆盖新通道。把旧 BM25 留作对照，固定样本比较召回与最终回答，不只比较语句是否更流畅。

## 例四：替换模型提供商

优先使用现有兼容协议。需要其他协议时，实现相同 complete 边界并归一化 ToolCall、usage 和错误。用协议假响应验证，再运行真实接口检查，最后执行业务评测。

## 面试讲解顺序

先讲用户和业务问题，再演示正常回答、依据不足和工单确认。接着画出 API、Agent、工具和存储关系，解释最重要的三个取舍：检索权限、来源验证、写操作确认。

用一次失败说明工程能力：例如通用词误召回、模型伪造引文、确认请求重试。说明如何发现、为什么发生、怎样修复、用什么测试防止回归。

最后报告有证据的指标，明确规则演示、协议 Mock 与真实模型评测的区别。当前单机 SQLite 和进程内任务的边界也应能讲清。

## 自检问题

- 为什么选择直接实现工具循环？何时应引入成熟编排框架？
- 为什么审核 Agent 不能替代权限检查？
- 任务中断与自动恢复到某个模型步骤有什么区别？
- 增加一个 Agent 如何证明值得？
- 引用完全真实，回答仍然可能错在哪里？

# 08 · 工作副本、差异与成果合入

源码入口：team/workspace.py 的 safe_path、file_map、Workspace。

每个任务 attempt 有 base、work 和可选 artifacts 目录。base 是启动时原项目的允许文件快照，work 从 base 复制，再叠加依赖成果。模型只通过文件工具访问 work。这样原项目不会因为模型的一次错误编辑立即改变。

文件扫描排除 .git、依赖目录、缓存、var、凭据目录、.env 和密钥/数据库文件等。单文件超过 1MB 跳过，项目超过 4000 个文件或 40MB 拒绝。这个后端面向适中项目，不适合将整个用户目录作为项目。文件扫描清单在 workspace.py 的 EXCLUDED / forbidden；有特殊资源需求需明确调整并补测试。

safe_path 拒绝绝对路径、..、冒号、禁止文件和符号链接/目录联接，再检查解析后路径仍在根目录。路径边界要在每次读写执行时检查，不能只相信模型说自己会遵守。

changes 比较 base/work 的 SHA-256，输出新增、修改、删除及统一 diff。交接只叠加依赖记录的变更，不盲目复制整个依赖目录；应用前验证依赖文件仍匹配完成时哈希，发现变更或冲突就停下。

apply 先验证当前 work 与完成清单一致，再比较原项目：如果已经等于目标哈希，跳过；如果等于基线，允许合入；否则说明用户或其他任务改过，拒绝覆盖。所有冲突先检查，再写文件。单文件用临时文件加 os.replace；正常异常会回滚已写文件。

这不是完整事务文件系统：断电或外部程序在检查与写入之间同时改文件，仍可能需要人工恢复。程序内 apply_lock 避免本应用自己并发合入；不会锁住所有外部编辑器。关键代码可以结合 Git 提交和备份。

未完成任务 resume 保存当前差异，新任务重新建立副本并叠加它，旧工具不会自动重放。若原项目已经发生冲突，仍会拒绝，避免用“恢复”覆盖新的工作。

自检：为何交接后的第二个任务也可能显示第一个任务的变更？答案：第二个任务以原项目为基线，work 包含依赖产物，因此它的最终变更包含尚未合入的依赖成果，便于交付完整结果。

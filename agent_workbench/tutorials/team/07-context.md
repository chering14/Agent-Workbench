# 07 · 共享上下文与 Token 成本

源码入口：runtime.context、group_updates、execute 中的 compact；db.reserve、settle、usage。

“大家知道同一个项目”通过结构化共享资料实现。任务启动上下文包含项目说明、自己的任务与职责、项目成员列表、依赖报告及文件、已启用扩展目录、最多 250 个文件名和近期群事件。文件全文由 read_file 按需读取，不默认塞入全部仓库。

每次模型请求前补充最新项目说明与近期消息。group_updates 在最近 60 条事件中选取消息、完成、合入和失败信息，最多 20 条，每条最多 2000 字符。它是有明确上限的近期上下文；更早的长期约定应写进项目说明或项目文件，不能假设模型始终看见全部历史。

历史工具输出较长时，较旧内容裁剪至 1500 字符，并提示需要时重新读文件。完整输出仍保留在 events。上下文超过当前大小阈值会停止并提示拆分任务，避免无限增长。这是可解释裁剪，不是语义摘要或向量长期记忆。

预算预留在 BEGIN IMMEDIATE 事务中完成。先读取累计 Token/金额，再判断本次预留是否超限，最后插入 call；两个并发任务不能同时认为自己拿到了最后一份预算。模型返回 usage 后再结算，缺失用量或请求失败时保留估算值。

```text
估算输入 = 序列化上下文与工具描述的 UTF-8 字节数 + 余量
预留 Token = 估算输入 + 本次最大输出
估算金额 = 输入 × 输入单价 / 1,000,000 + 输出 × 输出单价 / 1,000,000
```

字节估算是保守启发式，并非针对每种 tokenizer 的数学上界。供应商额外费用、缓存折扣、隐藏用量、外部工具费用也未完整纳入，所以页面显示的是应用账单估算。金额预算启用时必须填写输入输出单价；不填写不能把未知费用显示成免费。

节省成本需要实验：同一项目固定验收条件，分别用单个强模型和分层协作，比较完成率、总用量、返工次数与时间。便宜模型反复失败可能比强模型一次完成更贵。本项目不填写未经测量的节省百分比。

自检：为什么普通群消息不花模型 Token，却会影响下一次调用成本？答案：消息只落库时没有请求模型；之后它进入上下文，才随输入产生用量。

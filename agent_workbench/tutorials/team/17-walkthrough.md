# 17 · 一次项目从需求到交付，以及如何改功能

目标例子：做一个纯前端任务列表，支持新增、完成切换、剩余数量和刷新后保留。先在项目说明写清静态页面、中文界面、无账号、存储方式与验收点；选择两个真实成员，分别负责实现和审查。没有模型配置时用离线示例理解操作，但不要期望规则演示实现任意需求。

第一步，创建项目或指向一个已有的适中代码目录。页面 POST /api/projects，经 ProjectInput 校验，file_map 检查允许文件范围，存为 project。项目说明成为所有新任务共同上下文。

第二步，发送“自动规划”。message 路由保存群事件，create_task 选择负责人、创建 kind=plan 的任务。调度器领取后准备工作副本，context 汇总共同约定、成员和文件。模型通过 read_file 调查，submit_plan 返回条目，如“实现功能”与“验证边界和交接”，后者 depends_on=[0]。

第三步，你采用计划。validate_plan 检查成员与依赖；accept_plan 在同一事务建立全部草稿并标记采用。你看见任务分配后开始执行。第一位成员运行时，第二位仍 queued，因为前置任务尚未完成。

第四步，开发者通过 write_file/edit_file 修改 work。每次 HTTP 请求先 reserve 预算，返回后 settle 用量。工具结果写历史和事件；前端通过 SSE 看见当前过程。模型要求运行测试时停在 waiting_approval，你核对命令和 cwd 的工作副本位置后允许一次。

第五步，工具返回真实退出码和日志，模型可根据失败修复代码；最终 finish_task 提交报告。程序计算 diff 与文件哈希，标记 completed。请检查报告与工具记录是否一致，不能只看一段“全部通过”。

第六步，审查成员的依赖满足，工作副本获得开发成果和报告。它应检查空输入、连续点击、存储格式损坏、刷新恢复等条件，可运行静态页面浏览器检查。若发现问题，直接在自己的 work 修改，新的成果包括尚未合入的依赖变更。

第七步，你查看最终文件与差异，预览静态页面，核对实际测试，再合入。Workspace.apply 检查原文件是否仍匹配基线。若你在开发过程中手改原文件，冲突会阻止覆盖；先协调差异再继续，不把冲突当成可忽略提示。

如果中途失败，错误与副本保留。“保留文件，继续任务”把部分成果交给新任务，可换成员重新检查；“从原项目重新尝试”从原项目重建当前任务下一次 attempt。前者不是自动重放全部工具，后者不承诺保留失败版本到新副本。

现在沿真实调用链读代码：app.js composer → api.message → runtime.create_task → db.create/event → runtime._schedule → Workspace.prepare → runtime.context → ChatModel.complete → Pydantic 工具校验 → execute_tool → finish → SSE → showTask → control(apply) → Workspace.apply。能够讲清每一步的输入、输出、权限和失败方式，就掌握了项目的主要结构。

增加功能的正确顺序：先描述用户行为和验收，再修改契约与后端；补规则演示能覆盖的部分和必要行为测试；更新前端；浏览器验证；最后同步教程和交付说明。例如增加“删除文件”工具，应定义 FileInput 契约、描述、成员权限、safe_path 校验与 work 删除，再验证 diff 删除及合入冲突。不要只给模型加一句“你可以删除文件”。

如果要增加自动升级专家，先定义触发条件：工具失败次数、预算余量、模型输出是否满足验收；保存升级原因与新负责人；避免无限来回转交；用相同任务比较总费用和完成率。当前手动交接已经提供基础，但自动升级尚未实现，不能提前宣称。

自检与参考答案：为什么审查任务应有明确验收？因为另一个模型的笼统意见不能替代验证。为什么不直接共享一个可写目录？并发编辑会覆盖，难以判断谁改了什么。为什么记录未知计费而不是当作零？网络失败不代表供应商未处理。为什么本地无登录仍有写令牌？浏览器里的其他网站不应随意触发本机操作。

学习到这里，可将“我能在 AI 协助下完成项目”进一步变成“我能读懂边界、核对证据、定位失败并修改功能”。无需背熟所有库；能够从用户动作追到状态、工具和测试，才是后续独立维护最有用的能力。

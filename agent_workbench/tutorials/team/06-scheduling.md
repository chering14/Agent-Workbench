# 06 · 分工、依赖和调度状态机

源码入口：team/runtime.py 的 choose、create_task、_schedule、control。

调度器每 0.3 秒查看可运行任务。任务必须是 queued、未在 active 中、负责人未被占用、全部依赖 completed，才能进入 running。线程池上限为 3，同成员串行。没有满足依赖的任务会保留等待，不自动把失败依赖当成功。

```text
draft → queued → running → completed
                    ↘ waiting_approval → queued
                    ↘ failed / cancelled / interrupted
```

状态转换由 control 检查：只有 draft 可以 start，只有等待确认任务可以 approve/reject，只有 completed 执行任务能 apply。取消是显式状态和 cancel 标记，执行循环在关键点检查；完成写入与控制操作共用锁，避免用户已经停止却又被标成成功。

TaskInput 的依赖只允许当前项目已存在任务，因此新任务不会反过来形成环。模型规划中的 depends_on 使用 0 起始序号，只能指向前面条目。采用计划先校验所有成员与依赖，再在一个事务中创建草稿。规划不直接修改项目文件，也不给不具备文件能力的成员偷偷添加文件权限。

自动路由不是另一次 LLM 调用：choose 优先真实成员，再比较档位距离和输入单价。这样路由本身不花 Token，但不能理解复杂语义。需要语义分工时，使用“自动规划”让模型把不同任务分给成员，负责人检查后采用。

handoff 为已完成任务创建一个依赖它的新任务，保留旧报告。resume 对失败/停止/中断任务保存当前文件差异和错误线索，新建任务重新检查，不自动重放旧命令。retry 则增加 attempt、重新从原项目和原依赖构建副本；旧副本目录仍保留供排查。

不能直接启用 Uvicorn 多 worker：每个进程都有自己的调度线程和 active 集合，会抢同一数据库任务。若以后做多进程，需要数据库租约或外部队列、原子领取和心跳恢复，而不只是增大线程数。

自检：一个成员调用模型等待网络时，另一位能工作吗？答案：可以，前提是成员不同、任务依赖已完成且还有线程名额。文件冲突仍需在交接或合入时检查。

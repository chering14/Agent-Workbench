# 01 · 把工作群变成可执行的产品

源码入口：team/contracts.py、team/runtime.py。

项目保存共同目标、原目录、成员范围和预算。成员保存模型接口、模型 ID、角色说明、档位、单价、工具权限。任务保存具体目标、负责人、依赖、状态和成果。事件保存谁在什么时候做了什么。调用账本保存每次模型请求的用量。不要把这五类对象都混成聊天记录。

一个典型项目是“做一个本地记账网页”。负责人把页面原型交给经济档成员，把核心计算与边界检查交给专家档成员。第二个任务依赖第一个，因而会拿到第一个成员的报告和文件。角色名字可以叫“前端开发员”，实际模型可以随时更换；模型品牌不定义角色能力。

聊天有三种用途：只发消息、直接分配任务、请求生成计划。仅发消息在没有指定成员或唯一 @ 命中时，只保存事件，不调用模型。直接任务立刻排队；计划先产出结构化条目，采用后成为草稿，再开始执行。

群聊是统一入口，任务是可追踪的执行单元。任务完成并不自动合入，也不自动发布网站。“已完成”表示模型调用 finish_task 提交了报告；你仍应查看实际验证日志和 diff。“已合入”表示文件合入动作已经完成。

自动选择当前采用透明规则：优先已启用真实模型，比较任务档位与成员档位的距离，同距离按已填输入单价排序。它没有自动评测每个模型，也不保证最便宜总成本。模型规划则由选中的模型根据职责和目标提出分工，人负责采纳。

设计取舍：并行可以缩短独立任务等待时间，但多个 Agent 会重复读取上下文。任务划分过细会增加协调成本，划分过粗则容易超出步骤和上下文限制。先按可验收产物拆分：例如“一个页面及测试”，而不是“思考”“再思考”。

自检：为什么不让每条群消息都广播唤醒所有模型？答案：通常没有必要，会重复付费并产生相互回复循环。当前保留消息供后续调用读取，只唤醒被分配的执行者。

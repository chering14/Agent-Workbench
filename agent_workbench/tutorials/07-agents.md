# 07 · Agent 循环与独立审核

代码入口：`AgentService._run()`。完整应用的编排由应用负责，模型在允许的工具集合内选择下一步。

## 支持 Agent 的三个工具

`search_knowledge` 检索当前用户可访问资料。`prepare_ticket` 准备待确认草稿。`finish_answer` 返回结构化结论、状态和引用。只有最后一个工具通过校验，运行才可能结束。

每轮把模型请求追加为 assistant 消息，把工具结果追加为 tool 消息，然后进入下一轮。非法工具或无效引用会被拒绝，并允许有限次数修正，超过限制保存失败。

## 为什么循环必须有边界

模型可能反复检索、生成无效参数或迟迟不结束。应用设置最大模型调用次数、总时间、累计 token 和每次输出上限。达到限制时明确失败，避免无限消耗资源。

token 预算主要依据已返回 usage 结算。某次请求产生的 token 可能让累计值越过阈值后才停止，因此它不是供应商账单的绝对硬上限。要严格控制费用，还需供应商项目额度与代理层限制。

## 独立审核 Agent

候选结果先经过确定性引用校验，再调用另一套系统提示下的 reviewer。审核者只获得问题、候选结果和引用，不获得创建工单的工具。它通过 submit_review 返回批准与理由。

审核拒绝时，不发布原候选结论；返回依据不足，并取消该次草稿。这是一种受应用编排的双角色方案。它增加一次调用，有可能降低某些错误，也可能误拒，必须通过对比实验判断收益。

## 单 Agent 与双角色比较

设置 `LLM_REVIEW_ENABLED=false` 会关闭独立审核，但应用的权限、契约、来源校验和确认机制仍然执行。比较时固定数据集、模型、其他提示和判定规则，分别记录任务完成率、错误率、耗时及 token。

规则演示中的审核也由规则产生，只用于体验流程，不产生双模型效果证据。

## 上下文与记忆

完整消息持久化保存，但模型每次只取最近有限条历史，并限制每条长度。这样控制上下文和费用，也意味着较早信息可能不再进入模型。要做长期记忆，需要摘要、检索和更新策略，并评测记忆引入的错误。

练习：设计一个“总在搜索”的假模型，观察调用预算让它停止；再关闭审核，确认运行轨迹里少了 reviewer，理解状态为什么仍可正常完成。
